# План развития очистки CleanCore

Дата: 2026-10-15. Статус: частично реализован локальный кандидат 0.0.4. Фактические изменения, проверки и остаток — в [отчёте](reports/CLEANER_EXPANSION_2026_10_15.md). Исходное описание целевого поведения ниже остаётся планом, а не заявлением о полной готовности.

Документ подготовлен по запросу пользователя после сравнения открытых и коммерческих клинеров. Он описывает целевое поведение, последовательность внедрения и приёмку. Создание плана не означает выполнение его пунктов или разрешение удалять пользовательские файлы.

Основные требования: [ТЗ](../TECHNICAL_SPEC.md), [ROADMAP](ROADMAP.md), [безопасность](SECURITY.md), [модель угроз](THREAT_MODEL.md), [правила очистки](CLEANUP_RULES.md). Фактическое состояние: [STATUS](STATUS.md), [TASKS](TASKS.md).

Идентификаторы CLN-01–CLN-09 относятся только к этому плану и не заменяют номера этапов ROADMAP. Перед реализацией каждого модуля создать задачу по [шаблону](templates/TASK.md), связать её с ROADMAP/TASKS и определить владельца файлов. Сейчас меняется только этот документ; права на изменение параллельных модулей из него не следуют.

## 1. Цель

CleanCore должен позволять пользователю:

1. Находить мусор по проверенным правилам и понимать последствия очистки.
2. Просматривать полный доступный список кандидатов, выбирать объекты и исключения.
3. Отправлять поддерживаемые объекты в Корзину; безвозвратный режим выбирать отдельно.
4. Удалять выбранный файл или папку через контекстное меню карты после отдельного предпросмотра.
5. Различать кеш, личные данные, дубликаты и просто большие файлы.
6. Получать отчёт об успехах, пропусках, ошибках и неизвестных исходах.

Сохраняются Rust/Tauri/React, локальная работа и действующий запуск через UAC. Права администратора не отменяют проверки, не разрешают менять ACL и не превращают все доступные файлы в кандидатов очистки.

## 2. Отправная точка

| Область | Фактически есть | Чего ещё нет |
| --- | --- | --- |
| Диск | NTFS MFT-анализ, индекс, карта, переходы и размеры logical/allocated | Удаление из карты и обновление результатов после него |
| Правила | user-temp-v1: пользовательский Temp от 7 суток; user-temp-logs-v1: .log от 30 суток, только анализ | Каталог браузерных, прикладных и системных категорий |
| Исполнение | Отдельно подтверждаемый BoundDelete для user-temp-v1, повторные проверки, журнал | Допущенный адаптер Корзины и широкая приёмка Windows |
| Сканер очистки | Прогресс, отмена, предпросмотр, ограничения ресурсов | Продолжение больших задач без превращения лимита в тупик |
| Дубликаты | Размер → предварительный SHA-256 → полный SHA-256 | Постоянный кеш хешей, защищённые оригиналы и ручное удаление |
| Программы | Инвентаризация, запуск штатного удаления | Анализ остатков после удаления |

Два текущих правила пересекаются: старые журналы находятся в том же Temp. Их размеры нельзя складывать как независимые категории. MFT-анализ и сканер очистки — разные механизмы; ускорение первого не устраняет ограничения второго.

## 3. Обязательный общий сценарий

`Выбор категорий → сканирование → предпросмотр → выбор объектов → подтверждение → повторная проверка → исполнение → журнал → обновление отчёта`.

- Backend владеет снимком кандидатов, версиями правил, идентичностями объектов и разрешениями. UI передаёт идентификаторы, а не произвольный путь удаления.
- Подтверждение фиксирует точный набор, действие и снимок. Изменение выбора, режима или правил требует нового подтверждения. Токен ограничен сроком и не переиспользуется.
- Между задачами конфликтующие изменения сериализуются. Два окна/повторный клик не должны запустить двойное удаление.
- После перезапуска можно восстановить отчёт, но нельзя автоматически повторять незавершённую операцию или возобновлять старое разрешение.
- Перед действием проверяются идентичность, метаданные, предки, разрешённая область, ссылки, тип объекта и применимость правила.
- Занятый, изменившийся, недоступный или неопределённый объект пропускается. Процессы не завершаются, защита и ACL не изменяются.
- Неудача Корзины не переключает операцию на безвозвратное удаление.
- Предпросмотр ничего не удаляет. Отмена останавливает последующие действия; уже выполненное не объявляется отменённым или восстановленным.
- Сбой записи намерения блокирует действие. Сбой после действия даёт неизвестный исход, останавливает пакет и требует сверки.

## 5. Очередность внедрения

### CLN-01. Завершённое сканирование и достоверные результаты — P0

**Проблема:** текущие ограничения — глубина 8, 50 000 просмотренных объектов, 1 000 кандидатов и 60 секунд — могут завершать задачу без возможности исполнения. Нельзя просто убрать ограничения или разрешить любой незавершённый снимок.

**Реализация:**

- Разделить лимиты памяти, размер страницы, объём подтверждаемой партии и длительность одного отрезка работы.
- Хранить очередь обхода и снимок на backend; отдавать страницы с backend-поиском и сортировкой. Не отправлять весь список в React.
- Проектировать продолжение задачи с ограниченными ресурсами. Если безопасное продолжение недоступно, явно предлагать новое сканирование меньшей области.
- Различать running, complete, partial-access, paused-limit, cancelled, failed и устаревший снимок. Процент показывать только при известном знаменателе.
- До отдельного решения о новых правилах исполнения сохранять запрет исполнения после лимита/отмены/fatal. Проверенный partial-access допускается только по действующим условиям решения 005.
- Устранять пересечения правил по идентичности объекта; показывать несколько причин включения, но считать и выполнять один раз.

**Приёмка:** контролируемое дерево больше старых лимитов обрабатывается порциями без потери/повтора объектов; отмена и продолжение предсказуемы; preview не меняет файлы; причины неполноты видны; неполный отчёт не выдаётся за полный.

### CLN-02. Корзина и единый контракт исполнения — P0

**Сначала исследование:** Windows Shell принимает пути; проверка файла перед отдельным вызовом по пути не доказывает, что будет перемещён тот же объект. Описать в ADR гарантии выбранного адаптера, ограничения и гонки. Не обещать Корзину до прохождения отрицательных native-тестов.

**Целевое поведение:**

- Корзина — предпочтительный режим только для поддерживаемых и допущенных объектов.
- Если безопасная привязка операции к объекту не обеспечена, действие недоступно с объяснением. Карантин не называть Корзиной и не считать освобождением места на том же томе.
- Невозможность перемещения, лимит размера, отключённый диск и отсутствие Корзины дают отдельный результат без скрытого fallback.
- Безвозвратное удаление остаётся отдельным предупреждаемым действием; расширение за пределы user-temp-v1 требует отдельного допуска.
- Восстановление через Windows не обещает исходный путь и успех во всех случаях. Не добавлять кнопку «Отменить», если восстановление не реализовано.

**Приёмка:** восстановление собственных тестовых файлов; подмена файла/предка, junction, hard link, занятость, отказ доступа, исчезновение диска и сбой журнала; нет окончательного удаления при отказе Корзины. Недоказанный адаптер остаётся выключенным.

### CLN-03. ПКМ и удаление с карты — P0

Зависит от CLN-01/02 для включения изменяющих действий. Меню и read-only подготовку можно сделать раньше.

**Файлы:** ПКМ → «Переместить в Корзину…» → свежая проверка → окно с путём, размером и режимом → подтверждение → исполнение → результат. Безвозвратное действие появляется только после отдельного допуска.

**Папки:** дополнительная подзадача после файлов. Backend строит ограниченный свежий список содержимого, показывает количество, объём и пропуски. Подтверждение относится к этому списку; новые файлы не подхватываются. Удалять пустые каталоги снизу вверх только после проверки идентичности и пустоты. Частично обработанную папку не объявлять удалённой целиком.

- MFT-запись — источник выбора, но не готовое полномочие удаления. Проверять том, file ID/sequence и актуальные метаданные через файловый API.
- Агрегированные плитки «Прочее», категории расширений и неполные сводки не являются удаляемыми объектами.
- Запретить корни томов, файловые метаданные и защищённые области Windows; точный allowlist пользовательских областей оформить до включения. Большой размер не является основанием для удаления.
- Ссылки/reparse points и неподдерживаемые сетевые/съёмные расположения в первой реализации пропускать.
- Множественный выбор не должен дважды включать потомка выбранной папки.
- После операции помечать снимок затронутой области устаревшим и пересчитывать её. Не вычитать размер вслепую из всех итогов карты.

**Приёмка:** меню выбирает правильный объект при масштабировании/прокрутке; изменение между картой и подтверждением обнаруживается; чужой ID отклоняется; новые файлы в папке остаются; частичный успех отражён и на карте, и в журнале.

### CLN-04. Расширяемый каталог правил — P1

Сначала собственные локальные декларативные правила с ограниченным набором операций. В первой версии: обнаружение приложения, разрешённые корни, маски, возраст, исключения и обычные файлы. Никаких скриптов, произвольного shell, универсального удаления реестра или подключаемого исполняемого кода.

**Поля правила:** стабильный ID и версия; название/описание; приложение и профили; способ обнаружения; доверенные корни; включения/исключения; срок хранения; условие запущенного приложения; риск; последствия; разрешённые режимы; preview-only/допущено; источник и тестовые фикстуры.

- Пути разрешать через доверенные Windows API; переменные из чужого ini не становятся разрешёнными корнями.
- Профили обнаруживать отдельно; не ограничиваться Default и не чистить весь User Data.
- В elevated-процессе явно показывать, чей профиль сканируется. При UAC с учётными данными другого администратора не считать автоматически его профиль профилем исходного пользователя; неоднозначность блокирует персональные категории.
- Политика запущенного приложения: попросить закрыть и повторить проверку, не завершать его самостоятельно.
- Обновления правил первоначально поставлять со сборкой. Импорт, сеть и автообновление — отдельные будущие решения.
- Неизвестные поля/опасные операции отклонять. Ошибка одного правила видна и не разрешает его исполнение.

**Приёмка:** валидатор, отрицательные тесты путей и операций, несколько профилей, отсутствие приложения, активное приложение, конфликт правил, исключения и несовпадение версии снимка.

### CLN-05. Первая полезная библиотека категорий — P1

Каждую строку вводить отдельно: исследование реального расположения → собственное правило → preview-only → фикстуры/нативная проверка → допуск исполнения. Срок хранения и режим задаются для конкретного правила, а не общей константой для всех кешей.

| Очередь | Категория | Граница и последствия |
| --- | --- | --- |
| 1 | Пользовательский Temp | Довести текущее правило; свежие и занятые файлы пропускать |
| 2 | Кеш Chrome/Edge и затем Firefox | Только проверенные кеш-каталоги профилей; повторная загрузка данных; браузер закрыт |
| 3 | Пользовательские отчёты о сбоях | Возраст и назначение; предупреждать о потере диагностики; не читать содержимое дампов |
| 4 | Кеш миниатюр | Изучить штатный механизм и блокировки; объяснить последующее перестроение |
| 5 | DirectX shader cache | Проверить расположение и API; объяснить повторную компиляцию |
| 6 | Системный Temp и системные отчёты | Новые разрешённые корни и отдельная safety-приёмка; администратор не означает разрешение на любой файл |
| 7 | Кеши выбранных приложений | Добавлять по реальному использованию пользователя и отдельным фикстурам |

Cookies, история, пароли, сессии, Local Storage, IndexedDB, загрузки и документы в эту библиотеку кешей не включаются. Нельзя обещать конкретный объём освобождения до сканирования.

**Приёмка каждого правила:** целевые старые файлы найдены; свежие, исключённые и личные данные не затронуты; приложение запускается после очистки; каждый пропуск объяснён; правило и версия отражены в журнале.

### CLN-06. Приватность — P2

- Отдельные выключенные по умолчанию категории: история, cookies, сессии и данные сайтов. Сохранённые пароли первоначально не поддерживать.
- Показывать конкретные последствия: выход из аккаунтов, потеря сессий или локальных данных сайта.
- Для изменения SQLite/JSON и подобных хранилищ нужен отдельный тип операции, тесты целостности, проверка закрытого приложения и понятные ограничения восстановления. Не удалять профиль целиком.
- Не добавлять затирание свободного места, MFT/USN и обещания гарантированного уничтожения данных в эту очередь.

**Приёмка:** браузер сохраняет рабочий профиль; очищается только подтверждённая категория; остальные данные и выбранные исключения сохранены.

### CLN-07. Дубликаты — P2

- Сохранить сравнение размера, предварительного и полного хеша. Имя/расширение не доказывают одинаковое содержимое.
- Добавить кеш по идентичности, размеру, времени изменения и версии алгоритма с консервативной инвалидизацией. Хеш-кеш ускоряет анализ, но не заменяет проверку перед удалением.
- Защищённые папки-оригиналы не предлагаются к удалению. Пользователь вручную выбирает копии и видит оставляемые объекты.
- Перед исполнением убедиться, что доступная сохраняемая копия всё ещё существует и соответствует группе. Все копии группы удалить одним выбором нельзя.
- Повторно использовать допущенный исполнитель, Корзину и журнал. Hard links учитывать отдельно, не обещать освобождение места от удаления дополнительного имени.

**Приёмка:** одинаковые файлы с разными именами; разные файлы одинакового размера; изменение после кеширования; исчезновение оригинала; hard links; отмена больших задач.

### CLN-08. Приложения, разработка и системное обслуживание — P3

Три независимые подзадачи, без универсального привилегированного исполнителя:

1. **Остатки приложений:** после штатного удаления показывать предполагаемую связь с программой, основания и уверенность. Общие каталоги издателя и данные других приложений исключать. Поиск остатков первоначально только read-only; изменение реестра — отдельное решение с восстановлением.
2. **Кеши разработки:** анализировать выбранные проекты и конкретные менеджеры кеша. target, node_modules, пакеты и модели не считать мусором автоматически; объяснять пересборку, повторную загрузку и работу без сети. Удаление разрешать только для явно выбранной категории/проекта.
3. **Windows и виртуальные диски:** исследовать фиксированные штатные операции обслуживания Windows. Не удалять WinSxS/Installer/SoftwareDistribution обычным рекурсивным обходом. Docker/WSL VHDX показывать как хранилище данных; управление его содержимым и сжатием проектировать отдельно, без удаления самого диска как кеша.

**Приёмка:** правила связи не затрагивают общие данные; параметры штатных инструментов фиксированы и не приходят строкой из UI; результат проверяется отдельно от кода завершения; отсутствующие инструменты корректно объясняются.

### CLN-09. Приёмка, выпуск и документация — для каждого этапа

После каждой задачи обновлять TASKS/STATUS и отчёт по [шаблону](templates/REPORT.md), при необходимости CHANGELOG, API_CONTRACTS, SECURITY и CLEANUP_RULES. Реализовано, проверено на фикстурах и принято на Windows — разные отметки.

| cleaner-cleanup | Каталог, обнаружение приложений, обход, исключения, снимки и применимость |
| cleaner-execution | Подтверждение, повторная проверка, адаптеры действий, остановка и результаты |
| cleaner-storage | Миграции, журнал, настройки и кеши; не принимает решение об удалении |
| cleaner-disk | MFT/карта/дубликаты; подготовка выбора, но без обхода общего контура исполнения |
| cleaner-service | Инвентаризация и узкие фиксированные системные операции после отдельного допуска |
| src-tauri | Узкие IPC-команды и композиция сервисов; никаких delete(path) и shell(command) |
| React | Выбор, отображение, диалоги, доступность и обновление снимков |

Названия новых команд и DTO определить после чтения текущих API_CONTRACTS. Расширять существующий сервис, не создавать второй независимый удаляющий движок внутри карты.

Пример будущего контракта, не текущий API: prepare по scan_id/entry_id → preview_id; confirm по preview_id/набору ID/режиму → одноразовый token; execute по token → operation_id; progress/cancel/result по operation_id. Полномочия проверяет backend на каждом переходе.

## 7. Размеры и результаты

- Отдельно показывать логический размер, занятое место по доступным метаданным, размер успешно обработанных объектов и измеренное изменение свободного места.
- Перемещение в Корзину обычно не освобождает место на томе до её опустошения. Не подписывать размер перемещённых файлов как «освобождено».
- Изменение свободного места зависит и от других процессов; это наблюдаемая разница, а не точное доказательство результата CleanCore.
- Дедупликация кандидатов обязательна. Sparse/compressed/hard links и ограничения учёта named streams указывать, если они влияют на сумму.
- Успехи, пропуски, ошибки и неизвестные исходы считать отдельно. Не суммировать планируемые байты как фактически удалённые.

## 8. Матрица проверок

Все разрушающие проверки — на собственных фикстурах или снимках VM. Пользовательские файлы не использовать для автоматического удаления.

| Группа | Обязательные сценарии |
| --- | --- |
| Выбор/подтверждение | Ничего не выбрано; чужой ID; истёкший/повторный token; изменение режима; повторный клик |
| Пути | Traversal; UNC/device paths; junction/symlink/reparse; смена файла и любого предка |
| Объекты | Busy; Access Denied; hard links; исчезнувший/изменившийся файл; readonly; длинные и Unicode-пути |
| Папки | Новый потомок после preview; недоступный потомок; вложенный выбор; частичный результат; непустой каталог |
| Хранилище | Нет места; отказ журнала; авария между intent/action/result; миграция; запрет автоматического повтора |
| Масштаб | Более старых лимитов сканера; большие списки; ограниченная память; отмена; несколько задач |
| Интерфейс | Навигация во время scan; восстановление отчёта; клавиатура и фокус диалогов; DPI; правильная цель ПКМ |
| Платформы | Windows 10 x64 и Windows 11; NTFS; отказ UAC; другой администратор; прочие ФС явно поддержаны или отклонены |
| Приватность | Нет новых фоновых сетевых запросов; журнал без содержимого файлов/секретов; экспорт только по запросу |

На каждый изменяемый crate: целевые cargo test/clippy и проверка форматирования затронутых файлов. На UI: целевые Vitest, lint и build согласно package.json. Общий workspace прогон — отдельный release gate, не повод менять чужие модули. Команды и реальные результаты фиксировать; незапущенное не считать успешным.

Производительность измерять на описанном наборе: число файлов/каталогов, файловая система, характеристики ПК, холодный/повторный проход, время, пик памяти, скорость отмены и отзывчивость UI. Сравнение с WizTree допустимо только на одном наборе с объяснением различий учёта. Численные бюджеты утвердить по исходному замеру до оптимизации; сейчас это не обещание скорости.

## 10. Источники и заимствование

Исследование основано на публичных исходниках и официальной документации; коммерческие продукты не проходили локальный сравнительный тест безопасности. Ссылки на main/master могут меняться.
