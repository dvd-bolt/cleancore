# Решение 002 — параллельная разработка этапа 4

Дата: 2026-10-14. Статус: принято для разработки; активная Корзина не допущена.

## Контекст

Пользователь разрешил параллельные этапы 3/4 и поручил этап 4. Другая нейронка одновременно меняла общую папку и удаляла новые файлы; общий scanner ещё не публикует идентичность объектов. Требования модели угроз запрещают выпуск непроверенного pathname-based исполнителя.

## Решение

Изолированный Git worktree и ветка `codex/stage4-execution`. Отдельный `cleaner-execution` сохраняет lifecycle/confirmation, принимает Rust-only TrustedCandidate и зависимости журнала/действия через traits. Production адаптер закрыт; логика проверяется тестовым адаптером без удаления. Контракт объединения закреплён в [STAGE4_INTEGRATION](../STAGE4_INTEGRATION.md).

## Альтернативы

| Вариант | Следствие | Решение |
| --- | --- | --- |
| Писать одновременно в cleaner-cleanup | Повторная потеря файлов и конфликт контрактов | Отклонён |
| Сразу вызвать Корзину по пути после stat | Race после проверки, нет доказанного связывания цели | Отклонён |
| Ждать весь этап 3 без реализации 4 | Не выполняет запрос параллельной разработки | Подготовлены независимые компоненты |

## Последствия

Новые прямые dependencies: uuid 1.28.0 (Apache-2.0 OR MIT), windows-sys 0.61.2 (MIT OR Apache-2.0), оба уже присутствовали транзитивно и закреплены Cargo.lock. Чужой исходный код не копировался. SQLite миграция добавляет cleanup_operations, уникальный preview и durable намерения; recovery неизвестных результатов не запускает действий.

Проверки объектов используют owned File, OPEN_REPARSE_POINT и sharing restrictions. Основания: [Microsoft CreateFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [file identity](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-by_handle_file_information), [reparse points](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points-and-file-operations). Эти API не подтверждают безопасность будущей операции Корзины без отдельного анализа.

## Проверка

Результаты и непройденные сценарии в [отчёте](../reports/STAGE4.md). Решение о блокировке активного адаптера пересматривается после захвата идентичности во время scan и общей Windows приёмки 4.2–4.3. Этап не помечается полностью завершённым до выполнения этих условий.
