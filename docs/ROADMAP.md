# CleanCore — этапы, модули и использование открытого кода

Согласованная дорожная карта. Статусы выполнения — в [TASKS](TASKS.md), текущий контекст — в [STATUS](STATUS.md). Модули 0.1 и 0.2 выполнены; разработка приложения ещё не начата.

## 1. Принцип разработки

**CleanCore** развивается от простого монитора до полноценного центра обслуживания Windows. Каждый этап разбит на небольшие модули, которые можно реализовать и проверить отдельно.

Порядок работы: **модуль → проверки → коммит → следующий модуль → сборка этапа**.

Стек: **Rust + Tauri 2 + React + TypeScript + Vite**, локальное хранилище SQLite. Интерфейс — русский, тёмный. Название репозитория — `cleancore`, лицензия собственного кода — MIT.

Первый цикл реализации охватывает **этапы 0–2**. Следующие этапы подключаются после выполнения критериев готовности. Каждый этап завершается рабочим результатом, применимыми проверками, обновлением документов и кратким отчётом. Даты назначаются после первого рабочего прототипа. Версия 1.0 означает подтверждённую стабильность, а не только наличие функций.

Исторические номера этапов и недель в исходном ТЗ не совпадают с этой детальной дорожной картой. Здесь определена актуальная последовательность; обязательные требования безопасности ТЗ сохраняются. Наличие задачи не разрешает выполнять её за пределами текущего запроса пользователя.

## 2. Что использовать из открытых репозиториев

Проведён первичный обзор репозиториев, лицензий и отдельных исходников. Для Czkawka просмотрены обход каталогов и поиск дубликатов, для dua-cli — обход файлов, для BCUninstaller — сбор приложений из реестра. Это предварительный отбор; полноценный аудит выбранных частей входит в соответствующие модули. Дата исследования — 2026-10-13.

### Результаты обзора

- У Czkawka лицензирование различается между ядром, приложениями и ресурсами. Выбирать части по конкретному компоненту. Манифест ядра содержит много зависимостей для изображений, аудио и архивов: всё ядро не подключать ради дубликатов.
- В поиске дубликатов Czkawka полезны стадии: размер → предварительный хеш → полный хеш, обработка hard links и отмены.
- BCUninstaller реализован на C#: сбор записей реестра служит техническим ориентиром. Добавлять .NET-зависимость ради этого модуля не планируется.
- Готовый файловый обход или cleaner не доказывает безопасность удаления. Проверки объектов и исполнение CleanCore проектируются отдельно.

### Правила заимствования

Перед включением зависимости или исходника зафиксировать ревизию, проверить лицензию конкретных файлов и зависимостей, выбрать минимальную часть, сохранить авторство и уведомления, проверить Windows-совместимость, добавить собственные тесты и записать происхождение изменений. Библиотеки подключать через адаптеры; скопированные части изолировать и сохранять их лицензию. Проверенные источники и SHA — в [REUSE](REUSE.md).

**Обязательные условия:**

- Frontend передаёт идентификаторы выбранных объектов, а не новый список произвольных путей.
- Если выбранный объект или его окружение изменились, он пропускается.
- При невозможности безопасного использования Корзины окончательное удаление не подставляется.
- До начала изменений журнал должен быть доступен.
- После аварии незавершённый исход не объявляется успехом.
- Отмена останавливает последующие действия и не обещает отката завершённых.
- Размер обработанных объектов отделён от реально освобождённого места.

**Приёмка:** проходят Windows-тесты подмены файла и родительского каталога, junctions, занятых файлов, отказов доступа и журнала. При недоказанной безопасности действие не выпускается. Порядок реализации учитывает зависимость исполнителя от готового журнала, независимо от номера модуля.

## 4. Общие интерфейсы и критерии завершения

### Как модули взаимодействуют

- Мониторинг возвращает снимки с временем измерения и доступностью полей.
- Задачи имеют состояния: выполняется, завершена, отменена, ошибка.
- Сканирование создаёт preview с версией правил и идентификаторами объектов.
- Исполнение принимает выбранные идентификаторы из подтверждённого preview.
- Хранилище сохраняет настройки, намерения и результаты действий.
- Интерфейс отображает состояния, не решает допустимость файлов.
- ИИ получает сводки только для чтения.

Планируемые контракты — в [API_CONTRACTS](API_CONTRACTS.md), границы — в [ARCHITECTURE](ARCHITECTURE.md).

### Проверки каждого модуля

| Область | Обязательные проверки |
| --- | --- |
| Rust | cargo fmt --check, Clippy, тесты |
| Frontend | Lint, TypeScript, тесты поведения, production build |
| Сторонний код | Лицензия, происхождение, зависимости, интеграционные тесты |
| Мониторинг | Первый замер, недоступные поля, исчезновение процесса, сброс счётчиков |
| Сканирование | Отмена, ссылки, большие деревья, отсутствие изменений |
| Очистка | Подмена объекта, занятость, отказ доступа, повторное исполнение |
| Хранение | Отказ до и после действия, авария, миграции |
| Выпуск | Windows 10/11, установка без сети, обновление и удаление |

Модуль завершён после реализации сценария, выполненных проверок, описания ограничений и коммита. Непройденные проверки блокируют зависимые возможности. Если инфраструктура публикации недоступна, локальный результат и внешний блокер фиксируются отдельно; публикацию нельзя считать завершённой.

Собственный антивирус, универсальный privileged helper, автоматическое удаление и телеметрия в дорожную карту не входят.

## 5. Порядок фиксации результатов

Чек-лист [TASKS](TASKS.md) содержит ID, зависимости и наблюдаемую приёмку. [STATUS](STATUS.md) хранит краткий контекст, [CHANGELOG](../CHANGELOG.md) — фактические изменения. Для задач, отчётов и решений использовать [TASK](templates/TASK.md), [REPORT](templates/REPORT.md) и [DECISION](templates/DECISION.md).
