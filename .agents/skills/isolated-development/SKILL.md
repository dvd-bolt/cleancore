# Скилл: isolated-development (Изолированная параллельная разработка)

## 🎯 Назначение
Этот скилл применяется, когда над одним репозиторием **одновременно работают две или более нейросети (или агенты)**, либо когда разработка ведётся параллельными потоками над разными фичами/этапами.

Главная цель — **предотвратить конфликты, затирание чужого кода, случайные откаты чужой работы и несанкционированный рефакторинг**.

---

## 🧭 Протокол изоляции (The Isolation Protocol)

### 1. Явное определение границ (Scope Definition)
Перед началом любых изменений агент обязан четко классифицировать файлы репозитория на три категории:
1. **Зона ответственности (Target Scope / Белый список):**
   - Новые файлы, модули, компоненты и крейты, создаваемые исключительно для текущей назначенной задачи.
   - Полная свобода проектирования, написания кода, оптимизации и покрытия тестами.
2. **Точки сопряжения (Integration Points / Минимальное касание):**
   - Файлы конфигурации, роутинга, регистрации команд или общего состояния (например, `Cargo.toml`, `App.tsx`, `lib.rs`, `Header.tsx`, `types.ts`).
   - Правило: **вносить только минимально необходимые строки** для подключения своего модуля (импорт + регистрация).
   - Запрещено переформатировать весь файл, менять порядок чужих импортов или рефакторить соседние ветки логики.
3. **Зона неприкосновенности (Forbidden Scope / Чёрный список):**
   - Все файлы и папки, относящиеся к другим этапам, фичам или модулям, над которыми параллельно работает другая нейросеть.
   - Запрещено: изменять логику, исправлять «замеченные недочёты», удалять, переименовывать или форматировать.

## 🚫 Строгие запреты при параллельной разработке

1. **Запрет на деструктивные команды Git:**
   - ❌ **НИКОГДА** не выполнять `git checkout -- .`, `git restore .`, `git reset --hard` или `git clean -fd`.
   - Если в рабочей директории видны незакоммиченные файлы или модификации (`git status`), они могут принадлежать параллельно работающей нейросети. Их сброс приведёт к безвозвратной потере чужой работы!
2. **Запрет на «попутный» рефакторинг:**
   - ❌ Не трогать код других модулей, даже если кажется, что его можно улучшить или типизировать строже. Любая правка в чужом модуле гарантированно приведёт к конфликтам слияния (merge conflicts).
3. **Запрет на исправление чужих тестов:**
   - Если чужой модуль находится в процессе разработки и его тесты временно падают — **не лезть чинить его код**. Работать изолированно через флаги таргетирования тестов.

---

## 🧪 Правила таргетированного тестирования и сборки

В условиях, когда соседний модуль может быть временно недописан другой нейросетью:

1. **Приоритет таргетированных тестов:**
   - Всегда запускать тесты **только своего модуля/крейта**:
     ```powershell
     # Rust: тестирование конкретного крейта или конкретного файла
     cargo test -p <my-crate>
     cargo test -p <my-crate> --test <test_name>
     cargo clippy -p <my-crate> --all-targets -- -D warnings

     # Frontend: тестирование конкретного файла тестов
     npx vitest run src/path/to/my-feature.test.ts
     ```
2. **Проверка компиляции и сборки:**
   - Запуск `cargo check --workspace` или `npm run build` для проверки того, что добавленные точки сопряжения не нарушили контракт сборки всего проекта.

## 📋 Чек-лист агента при каждом шаге

- [ ] Моя текущая задача чётко ограничена (известно, какой именно модуль я делаю).
- [ ] Я проверил `git status` и не трогаю чужие изменённые файлы.
- [ ] Все новые сущности созданы в изолированных папках/файлах текущей фичи.
- [ ] В общих файлах (роутер, стейт, конфиг) добавлены только строгие минимальные строки подключения.
- [ ] Тесты запущены изолированно для моего модуля и успешно пройдены.
- [ ] Чужой код остался нетронутым.
