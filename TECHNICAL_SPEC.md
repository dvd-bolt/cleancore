# CleanCore
Техническое задание и архитектура Windows-клинера
Rust · Tauri 2 · React / TypeScript · Windows 10 x64
Версия документа: 1.0 · Статус: проект технического задания

## 1. Краткое описание проекта

CleanCore — бесплатная open-source утилита для обслуживания и мониторинга Windows. Приложение должно помогать пользователю анализировать состояние системы, находить безопасные варианты очистки и управлять отдельными системными объектами без скрытых действий и телеметрии.
- Целевая ОС: Windows 10 x64. Совместимость с конкретными редакциями и сборками должна проверяться тестами.
- Язык интерфейса первой версии: русский.
- Визуальный стиль: тёмная тема, аккуратный минималистичный интерфейс.
- Модель распространения: открытый исходный код, бесплатно.
- Приватность: локальная работа, без телеметрии и обязательного облачного аккаунта.
- Принцип действий: сначала анализ и предварительный просмотр, затем явное подтверждение пользователя.
- Долгосрочная цель: исследование защитных функций; собственный антивирус не входит в первую версию.

## 2. Критические ограничения и принципы

Полный набор из десяти модулей, продвинутый мониторинг, безопасная очистка, управление автозагрузкой, локальный ИИ и будущий антивирус — слишком большой объём для первой версии и для разработчика, который только начинает изучать Rust. План «прототип за несколько недель» реалистичен только при жёстком ограничении MVP.
- Не пытаться выпускать все модули одновременно. Сначала реализовать один полностью безопасный сценарий от сканирования до журнала.
- Не запускать всё приложение с правами администратора. Основной процесс должен работать с правами текущего пользователя.
- Не удалять файлы автоматически и не выбирать автоматически, какой дубликат оставить.
- Не обещать восстановление каждого системного изменения: откат зависит от типа объекта и доступных резервных копий.
- Не называть продукт антивирусом до разработки, тестирования и независимой оценки полноценной защитной системы.
- Не добавлять фоновые сетевые запросы, облачную аналитику или передачу данных без отдельного решения и явного согласия.

## 3. Цели и нецели

### 3.1 Цели

- Показывать основные показатели системы и список процессов.
- Сканировать разрешённые категории временных файлов и показывать предварительный список очистки.
- Требовать явное подтверждение перед изменением данных.
- Вести локальный журнал выполненных действий и ошибок.
- Обеспечить расширяемую архитектуру для будущих модулей.
- Сохранять отзывчивость интерфейса при сканировании и мониторинге.

### 3.2 Не входит в MVP

- Собственный антивирус, драйвер ядра, перехват файловых операций и постоянная защита в реальном времени.
- Автоматическая очистка без подтверждения.
- Автоматическое удаление дубликатов.
- Массовое изменение системных настроек и служб.
- Облачный ИИ, аккаунты, телеметрия и удалённое управление.
- Автоматические обновления приложения: обновления в первой версии запускаются вручную.

## 4. Архитектурный стек

| Слой | Решение | Назначение |
| --- | --- | --- |
| Язык и toolchain | Rust stable; фиксированная версия toolchain | Основная логика, безопасная работа с системными API |
| Desktop shell | Tauri 2 | Окно приложения, системный трей, команды frontend ↔ backend |
| Frontend | React + TypeScript + Vite | Компоненты интерфейса и страницы модулей |
| UI | Tailwind CSS + shadcn/ui или аналогичный набор | Тёмная тема и единая дизайн-система |
| Windows API | windows / windows-sys | Типизированный доступ к API Windows по мере необходимости |
| Асинхронность | Tokio — только там, где оправдано | Длительные операции, задачи и отмена |
| Модели данных | Serde / serde_json | Сериализация команд, настроек и результатов |
| Локальное хранилище | SQLite + rusqlite | Журнал, настройки и метаданные сканирования |
| Ошибки | thiserror + anyhow | Типизированные ошибки библиотек и контекст ошибок приложения |
| Логи | tracing + tracing-subscriber | Диагностика с локальным хранением и без секретных данных |
| Хеширование | sha2 | Сравнение содержимого файлов при поиске дубликатов |
| Тесты frontend | Vitest + React Testing Library | Проверка компонентов и поведения интерфейса |

sysinfo можно использовать для базовых метрик CPU/RAM, процессов, дисков и сетевых интерфейсов. Для глубоких сведений о потоках, издателе, цифровой подписи и отдельных сетевых соединениях могут понадобиться дополнительные Windows API. Не следует считать, что одна библиотека предоставляет все данные.

## 6. Поток данных и взаимодействие слоёв

1. React UI отображает данные и отправляет строго определённые команды.
1. Tauri commands проверяют входные данные, права вызова и допустимость операции.
1. Сервисный слой выполняет бизнес-логику и возвращает типизированный результат.
1. Системный слой вызывает Windows API или файловые операции.
1. Storage сохраняет настройки и журнал локально.
1. Длительные задачи должны поддерживать отмену, сообщать прогресс и не блокировать UI-поток.
Frontend не должен передавать backend произвольные команды оболочки или произвольные системные операции. Команды Tauri должны быть небольшими, конкретными и иметь валидируемые аргументы.

## 7. Безопасные границы привилегий Windows

- MVP запускается с обычными правами пользователя.
- Мониторинг и очистка пользовательских временных файлов по возможности выполняются без elevation.
- Административные действия не включаются в MVP. Позднее для них можно создать отдельный небольшой helper-процесс с узким allowlist API.
- Не запускать PowerShell, cmd.exe или другие оболочки с данными, пришедшими из UI.
- Не предоставлять frontend универсальную команду «выполнить действие от администратора».
- Ограничить Tauri capabilities: только необходимые окна, команды и разрешения.
- Не использовать драйвер ядра. Он увеличивает риски, стоимость тестирования и последствия ошибок.
- Ошибки Access Denied должны отображаться как штатный результат, а не обходиться повышением прав автоматически.

## 8. Безопасность очистки

Каждая операция очистки проходит последовательность:
1. Сканирование только по явным правилам из каталога очистки.
1. Проверка путей, типов объектов, доступности и исключений.
1. Формирование предварительного списка с категорией, путём, размером и риском.
1. Показ пользователю ожидаемого результата и потенциальных последствий.
1. Явное подтверждение конкретной операции.
1. Повторная проверка объекта непосредственно перед изменением.
1. Выполнение операции и запись результата в журнал.

### 8.1 Обязательные защитные меры

- Защита от path traversal и проверка reparse points, junctions и symlinks; не полагаться только на сравнение строк путей.
- Системные каталоги и пользовательские документы исключены по умолчанию.
- Не удалять файл, если он используется; не завершать процесс автоматически ради очистки.
- Не выбирать автоматически дубликат, который следует оставить.
- По возможности использовать Корзину для поддерживаемых пользовательских файлов; понимать, что не все операции можно откатить.
- Журналировать время, категорию, путь или безопасный идентификатор объекта, действие и результат; не записывать лишние персональные данные.
- Повторно проверять объект после сканирования, так как он мог измениться до подтверждения.
- При сомнении пропускать объект и объяснять причину.

## 10. Требования к MVP

### 10.1 Мониторинг

- Отображать CPU, использование памяти, дисковое пространство и сетевую активность интерфейсов.
- Показывать список процессов с PID, именем и доступными показателями потребления ресурсов.
- Обновлять данные по заданному интервалу без блокировки интерфейса.
- Показывать отсутствие данных как «нет данных», не подменять его выдуманными значениями.
- Отмена/остановка фоновых задач и корректная обработка исчезнувших процессов.

### 10.2 Очистка

- Одна-две безопасные категории пользовательских временных файлов для первой демонстрации.
- Сканирование без изменений на диске.
- Предварительный список найденных объектов и оценка потенциально освобождаемого места.
- Исключения, пропуск недоступных или изменившихся файлов.
- Явное подтверждение и запись каждого результата в журнал.
- Набор тестов на пути, junctions, доступ запрещён, файл занят и изменение файла между scan и execute.

### 10.3 Настройки и журнал

- Хранить локальные настройки и историю действий в SQLite.
- Давать пользователю очистить журнал вручную.
- Не отправлять телеметрию и не выполнять сетевые запросы для аналитики.
- Сделать запуск приложения в режиме без сети полностью рабочим.

## 11. Локальный ИИ и антивирус в будущем

Локальный ИИ следует добавлять только после того, как базовые функции и модель безопасности стабилизированы. Его первая роль — объяснять метрики, журналы и результаты сканирования. Он не должен иметь прямого доступа к выполнению очистки, изменению реестра или отключению защиты.
Собственный антивирус — отдельный исследовательский проект. Потребуются модель угроз, безопасная обработка недоверенных файлов, механизм обновления сигнатур, набор тестовых образцов, измерение false positives/false negatives, устойчивость к обходам и независимая оценка. До этого продукт не следует позиционировать как замену Microsoft Defender.

Срок в четыре недели — ориентир для прототипа, а не обещание готового продукта с полным набором модулей. Если разработчик новичок в Rust, лучше сократить функции, чем снижать требования безопасности.

## 13. Тестирование и критерии приёмки

| Область | Проверки / критерии |
| --- | --- |
| Очистка | Dry-run не меняет файлы; preview соответствует исполнению; ошибки отображаются; журнал отражает результат. |
| Безопасность путей | Тесты на traversal, junction/reparse point, symlink, относительные пути и смену цели после сканирования. |
| Дубликаты | Хешировать содержимое потоково; одинаковые имена не считаются доказательством дубликата; удаление не автоматизируется. |
| Системные ошибки | Access Denied, файл занят, объект исчез, диск отключён — безопасный отказ без падения. |
| Производительность | Сканирование не блокирует UI; задачи отменяются; большие каталоги не загружаются целиком в память. |
| Приватность | Нет телеметрии; проверка исходящего трафика; все журналы локальные. |
| Установка | Чистая установка/удаление в тестовой VM; корректная обработка отсутствующих разрешений. |
| CI | cargo fmt --check, cargo clippy, cargo test; frontend lint/test/build; аудит зависимостей и лицензий. |

## 14. Лицензия и публикация

Для проекта можно рассмотреть MIT или Apache-2.0. Перед выбором нужно проверить лицензии всех прямых и транзитивных зависимостей и определить, нужен ли явный патентный grant. Для открытого проекта стоит добавить README, CONTRIBUTING, SECURITY.md, описание поддерживаемых ОС, политику сообщения об уязвимостях и инструкции воспроизводимой сборки.
- Закреплять зависимости и сохранять Cargo.lock для приложения.
- В CI выполнять аудит уязвимостей и лицензий.
- Публиковать контрольные суммы релизов; подпись установщика можно добавить позднее.
- Указывать, что Windows 10 достигла окончания обычной поддержки 14 октября 2025 года; доступность обновлений безопасности зависит от ESU и конкретной редакции.

## 15. Риски проекта

| Риск | Последствие | Снижение риска |
| --- | --- | --- |
| Слишком широкий MVP | Проект не завершится в срок | Сначала мониторинг + одна категория очистки; остальные модули — поэтапно. |
| Удаление не того файла | Потеря данных или нестабильность системы | Preview, явное подтверждение, path guards, повторная проверка и тесты. |
| Избыточные права | Увеличение ущерба при уязвимости | Не запускать всё приложение от администратора; отдельный helper позже. |
| Неполные данные мониторинга | Пользователь неверно понимает состояние системы | Показывать источник/ограничения и «нет данных», не выдумывать значения. |
| Ложные срабатывания безопасности | Паника или удаление нормальных файлов | Не заявлять «вирус» без достаточных оснований; объяснять уровень уверенности. |
| Изменения Windows API | Поломки на отдельных сборках | Тестировать на чистой VM и обрабатывать отсутствие API/прав. |
| Неопытность с Rust | Сложность отладки и архитектурные ошибки | Малые crates, строгие типы, тесты, документация, постепенное расширение. |

## 16. Первый вертикальный сценарий

1. Пользователь открывает приложение.
1. Dashboard показывает реальные доступные метрики.
1. Пользователь открывает модуль очистки и запускает сканирование одной разрешённой категории.
1. Приложение показывает список объектов, размер, категорию и возможные ограничения.
1. Пользователь подтверждает конкретное действие.
1. Backend повторно проверяет объекты и выполняет только разрешённую операцию.
1. Результат и ошибки записываются в локальный журнал.
1. Пользователь может открыть журнал и увидеть, что было обработано.
Это рекомендуемый критерий завершения версии 0.1. Когда этот путь безопасен, покрыт тестами и стабилен, можно расширять каталог очистки и добавлять следующие модули.

## 17. Итоговая рекомендация

Начать с CleanCore 0.1: тёмный интерфейс, live-метрики, список процессов, безопасное сканирование временных файлов, предварительный просмотр, подтверждение, локальный журнал и базовые тесты. Не включать в первую версию автоматическое изменение системных параметров, собственный антивирус и автономные действия ИИ. Архитектуру сразу строить так, чтобы новые модули подключались без переписывания ядра.
